# Server tools

Four tools that answer about the server itself rather than the code. None record telemetry.

# `ping`

Health check. `Ping()` → `"pong dotnet-toolkit/<version>+build.<id>"`, e.g.
`"pong dotnet-toolkit/1.0.1+build.b921afb2"`. No arguments.

Both halves are read off the running assembly, so they report what is actually loaded. The **version**
catches a `dist/` that is a release behind — a mismatch against `.claude-plugin/plugin.json` means
`dist/` is stale, not that the doc drifted. The **build id** catches what the version cannot: two
binaries built from different sources under one version number, which is exactly the state that made
a "the server picks the wrong SDK" report impossible to attribute to source or binary. It is the
assembly's module version id, freshly generated by every compilation, so it cannot be typed into a
manifest by hand — two artifacts sharing one is evidence they are the same build.

Compare it against the published binary with
`dotnet <pluginRoot>/dist/DotnetToolkit.McpServer.dll doctor --no-probe`, which also fails when
`dist/` has fallen behind `src/`. After republishing, a session keeps serving the old in-memory build
until the server restarts; a `ping` still reporting the previous build id is that, not a failed
publish.

# `set_output_format` — change how responses are encoded

| Arg | Meaning |
|---|---|
| `format` | `json` (pretty-printed) \| `compact` (minified JSON) \| `toon` (default). |

Takes effect immediately and persists for the rest of the session (until changed again or the server
restarts). Returns a plain confirmation string, not a JSON/TOON envelope — e.g.
`set_output_format(format: "json")` → `"output format set to json"`. An unrecognized `format` is reported
back rather than silently defaulting: `"unknown format: yaml (use json|compact|toon)"`.

# `workspace_status` — is the index/workspace warm

Call this when a semantic tool reports the workspace isn't ready, before trusting a `0` reference
count, **or to resolve where the plugin's own files live** — see `pluginRoot` below.

Real response, this repo:

```
root: /path/to/dotnet-toolkit
pluginRoot: /path/to/dotnet-toolkit
solution: dotnet-toolkit.slnx
index: ready 133 files, 220 types; symbols refreshed 4s ago
workspace: loaded 2 projects in 2.3s
  loaded: DotnetToolkit.McpServer, DotnetToolkit.McpServer.Tests
```

`root` is the **target repository** being analysed. `pluginRoot` is where **the plugin itself** is
installed; in this repo they coincide, because the plugin analyses its own source tree.

## `pluginRoot` — the only way to reach the files that ship with the plugin

Claude Code substitutes `${CLAUDE_PLUGIN_ROOT}` in `.claude-plugin/mcp.json`, hook commands and skill
content — but **not** into a rule file or an agent definition, and it is not exported as an
environment variable a shell can read. So an always-loaded rule cannot name a path to the plugin, and
neither can a subagent. `workspace_status` reports the value instead, derived at runtime
(`CLAUDE_PLUGIN_ROOT` if the harness set it, otherwise the directory above the running assembly —
Codex's absolute MCP registration and both hosts' hooks run the assembly from `<pluginRoot>/dist/`). That makes it correct on any machine
and any plugin version, with nothing stored to go stale.

Join it to reach either shipped tree:

| Want | Path |
|---|---|
| A tool manual | `<pluginRoot>/docs/tools/<tool>.md` |
| A coding standard | `<pluginRoot>/standards/<name>.md` |

Each is the single location for that file. Nothing is copied into a consuming repo and there is no
per-repo override tier, so a resolved path is the answer — there is no second place to look.

Added in contract **3.50**. A server that omits the line predates it and needs republishing to
`dist/`; the `dotnet-read`/`dotnet-write` skills and `agents/dotnet-code-review.md` all treat its absence as a
reason to report standards-derived work as not-assessed rather than to guess a path.

The `index:` line also says when the symbol store last followed an edit (`symbols refreshed Ns
ago`) and, while a refresh is still running, how many files are queued (`, 3 file(s) queued`).
Both come from the `refresh-cs-files` hook and the sweep, which re-index just the files a tool
wrote; "queued" is the state to wait out before trusting `search_index` on a file you just changed.

A degraded workspace names the failing project — reference edges from a project MSBuild couldn't
evaluate contribute nothing, and semantic results from it are incomplete or wrong, not just thin.

## `knowledgeCache` and `msbuild` — the two lines that appear only when something is wrong

Both are absent while the session is healthy, so they cost nothing on the common path. Added in
contract **3.102**.

| Line | Appears when | What it means, and what to do |
|---|---|---|
| `knowledgeCache: …` | The SQLite knowledge cache is damaged | Symbol search and reference counts are disabled **for this session**, deliberately: a damaged store keeps answering from whatever pages still read, and a caller cannot tell that frozen snapshot from a current answer. The file is quarantined beside itself as `knowledge.db.corrupt-<timestamp>` (only the newest two quarantines are kept) and rebuilt from source on the next server start — every table is derived, so nothing is lost; deleting `knowledge.db` rebuilds it immediately. The server's stderr log names the pid and session id that opened each store, so a shared cache directory can be read back to the process that quarantined it. |
| `msbuild: …` | The workspace is not cleanly loaded, **or** no installed SDK satisfies this repository's `global.json` | Read it before blaming a tool. An unsatisfied pin reaches a caller as an unresolved `Microsoft.Build.Framework, Version=15.1.0.0`, which names neither the SDK that was chosen nor the pin it failed to match; this line names both. |

# `reload_workspace` — force a re-scan

| Arg | Meaning |
|---|---|
| `scope` | `index` (re-scan file index) \| `workspace` (re-open the MSBuild solution, then rebuild the SQLite symbol index/project graph) \| `all` (default). |

Call after a large external change the mtime-poller might not have caught yet in time — a `git
checkout`, a `git pull`, a rebase — or when the `refresh-cs-files` hook reported that the server was
unreachable for a new or deleted file. An ordinary `Edit`/`Write` does **not** need it: the hook
re-indexes the written files itself, and the sweep converges on anything the hook missed within a
couple of seconds. `workspace`/`all` queues a background `SymbolIndexBuilder` rebuild after
reopening the solution, so `search_index`/`get_references` catch up on the new symbols and edges
without waiting for the next periodic full sweep. That rebuild runs in the
background — `reload_workspace` returns before it finishes; check `workspace_status` if you need to
confirm it's done.

# `set_hook_guards` — suspend or force the C# read guards, briefly

| Arg | Meaning |
|---|---|
| `state` | `suspend` \| `block` \| `restore`. |
| `minutes` | How long to suspend/block for. Default 30, capped at 240. Ignored when restoring. |

There are no write guards: `Edit`/`Write` on a `.cs` file is the write path, and a `PostToolUse`
hook re-indexes what was written. Two `PreToolUse` guards remain, both on **reads**: a whole-file
`Read` of a compiled `.cs` file, and a whole-file shell read (`cat`/`grep`/`sed`/…) through `Bash`.
By **default** they are advisory — the call is allowed, with a note that `get_symbol` plus a ranged
`Read` would likely have cost less. A ranged read (`Read` with `offset`/`limit`, `sed -n 'a,bp'`,
`head -n`, `tail -n +N`) draws nothing in any mode. This tool moves both guards to a different
state for a bounded window:

- **`suspend`** — no advisory at all. Simulates a session with no plugin installed.
- **`block`** — the two read guards hard-deny a whole-file raw read instead of advising, so a probe
  cannot quietly fall back to `cat`.
- **`restore`** — back to the default: advise.

The legitimate uses are the ones where an unguarded or a forced path *is* the subject: measuring
these tools against `grep`/`Read` (`suspend`), reproducing what a repo without the plugin does
(`suspend`), or holding a probe to the MCP route (`block`). Since 2026-09-20 even
`dotnet-performance` does not call this by default: its three probes all run at the default state,
and the tool-call meter counts each probe's whole-file `.cs` reads (`wholeFileCsReads` in
`get_retrieval_metrics`) instead of denying them up front — Claude Code's auto-mode classifier
refuses a guard-state switch as self-modification, and a benchmark that cannot run in auto mode is
not run. Only the skill's opt-in strict variant, outside auto mode, uses `suspend` and `block`.
Outside a measurement, an advisory is guidance to weigh, not a wall to route around, so there is
nothing here to reach for.

A suspend or a block is stored as an **expiry, not a flag**. The state file under
`.claude/dotnet-toolkit/cache/` names the instant the guards resume and which of the two states is in
force; any read past that instant deletes it, and the cap bounds what can be asked for — so there is no
way to disable or force the guards indefinitely from here, and nothing has to remember to undo it.
While one is in force, `workspace_status` prints `hookGuards: SUSPENDED` or `hookGuards: BLOCKED` with
the time remaining; that line is absent when the guards are in their default state, so it costs nothing
in the normal case and is impossible to miss in the abnormal one.

`DOTNET_TOOLKIT_DISABLE_HOOKS` is the separate, non-expiring escape hatch, for a harness that owns the
whole process lifetime (CI, a benchmark runner) where "until this process exits" is already a bound.
`restore` cannot clear it — it lives in the server's own environment — and says so rather than
reporting a restore it did not perform.

## Next steps

- **`workspace_status` says `index_only`** → wait for the load, then re-fetch. **`stale`** clears on
  the next sweep by itself; `reload_workspace` only after a git operation or a file add/delete the
  hook could not deliver.
- **`degraded`** → fix the build first; results may be silently wrong, not just thin.
- **`hookGuards: SUSPENDED` or `BLOCKED` and you did not ask for it, or a `Read` on a `.cs` file
  denies unexpectedly** → `set_hook_guards(state: "restore")`; an earlier session in this repo left
  a window running.

## Where the raw route wins

Four places, and two of them are substantive:

1. **Q9, on correctness.** Counting occurrences of a literal string that are *not* code references is
   a raw-text question, and the MCP surface has no tool that answers it. Worse, it has a field that
   looks like it does. The raw route answered it correctly and the MCP route did not.
2. **The partial-class claim is overstated for a grep-first raw route (Q3, Q10).** The always-loaded
   rule says text search "returns one fragment of a partial class with no signal the rest exists."
   That is true of `Read`, and it was *not* true here: `grep "class SymbolStore"` returns every
   partial declaration at once, so the raw agent saw both files immediately and got both questions
   right. The MCP route still won these rows on cost by a wide margin, but the *correctness* claim as
   currently worded did not hold against a competent grep user, and I'd recommend the rule's wording
   be narrowed to `Read`/`cat` rather than "text search" generally.
3. **Q5 and Q8, on call count.** Finding implementers of an interface with exactly one implementer,
   and filtering a common method name, both fell to a single well-chosen grep where the MCP route
   spent 2–3 calls. On a repo this size these are genuinely close.
4. **Small, well-located files.** Q11's target is a 17-line interface. Once you know the path, `Read`
   is one cheap call, and the MCP route's advantage is only that it needed no separate step to find
   the path.

What I checked and did *not* find: any row where the raw route was both cheaper *and* right on a
dispatch question. Q6 is the case that decides this, and the raw route lost it in the specific way the
plugin predicts — a call written without the receiver prefix its grep pattern assumed.

## What this does and does not transfer to

Size axes: **2 projects, 155 indexed files, 254 types, 96 `.cs` files under `src/`, largest source file
2818 lines.** This is a small repo, which systematically *favours* the raw route: grep's cost scales
with tree size, and the MCP tools' per-call overhead is close to fixed. A 3× context saving here is a
floor, not a ceiling.

Rows that would plausibly flip on a much **smaller** repo (say under 40 files):
- Q1, Q5, Q8, Q11 — already near parity; a smaller tree makes grep cheaper still and these become raw
  wins.
- Q3/Q10 (partial classes) would stay a raw-correctness win as long as the agent greps rather than
  reads, and the file is small enough to read whole.

Rows that would widen on a much **larger** repo:
- Q4 (read one method out of a large file) — the file read has no way to return less than the file,
  so this scales linearly against the raw route while the MCP cost stays flat. `ContextTools.cs` at
  2818 lines is already the single biggest contributor to the raw route's 37.5k response tokens.
- Q6 and Q7 (dispatch, and safe-to-delete) — more implementers and more call sites mean more greps,
  more manual type inference per site, and more chances to miss a receiver-less call. The raw route's
  Q6 failure mode gets strictly more likely as the codebase grows.
- Q2 (fuzzy name) — the raw route's cost here is the number of guesses, which grows with vocabulary.

Rows that would not move much: Q7 and Q9 are both near-fixed cost on either route.

One axis this run does **not** measure: the raw probe ran on WSL against `/mnt/c`, where filesystem IO
is slow. That shows in wall-clock (257s vs 94s) but not in tokens, and tokens are what this report is
about. A Windows-native or PowerShell-only session would likely look worse for the raw route on both
axes, but that is an extrapolation, not a measurement taken here.

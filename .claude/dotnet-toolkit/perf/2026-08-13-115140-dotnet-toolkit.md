## FINDING 1 (blocking) — `set_hook_guards` silently fails to suspend anything

**A suspension taken by the MCP server is written under a session id the hooks never look for.**
The tool reports success, `workspace_status` reports `hookGuards: SUSPENDED for another 22 min`,
and the guards stay fully armed for every tool call in the session.

Mechanism, from `Hooks/GuardSuspension.cs`:

- `Suspend()` writes `.claude/dotnet-toolkit/cache/guards-suspended-until.<sessionId>` where
  `sessionId` comes from `CurrentSessionId()` → the `CLAUDE_CODE_SESSION_ID` env var **of the
  process making the call**, i.e. the long-lived MCP server.
- `Current()`, called in each hook process, checks the scoped file for *its own*
  `CLAUDE_CODE_SESSION_ID`, then falls back to the unscoped global file, then defaults to
  `Active` (guards on).

Observed this run:

| | session id |
|---|---|
| file the server wrote | `guards-suspended-until.183950ec-3d8a-4deb-bd4f-4832075c69b7` |
| `CLAUDE_CODE_SESSION_ID` in a live hook/shell process | `9ddc8510-9a36-4d3c-ae45-d2049e58d32e` |

The scoped lookup misses, the global file does not exist, so `Current()` returns `Active` and the
guard denies. Both directions of the fallback are individually reasonable; together they fail
silently and in the *safe* direction, which is why nothing ever caught it.

**Trigger:** the MCP server outlives the session that launched it. A resumed or continued session
gets a new `CLAUDE_CODE_SESSION_ID`, while the server keeps the one from its own launch
environment. Anything that restarts the session without restarting the server reproduces it, which
is the ordinary case, not an edge case.

**Blast radius:** `set_hook_guards` is the only sanctioned entry point for this, and
`dotnet-performance` is its only sanctioned caller — so the practical effect is that the raw probe
cannot run, and this skill cannot produce a comparison at all, on any session where the ids have
diverged. It is not a data-loss bug: it fails closed.

**Why the report is emphatic about it:** the tool returned a success string and `workspace_status`
corroborated it. Two instruments agreed the guards were down while they were up. A benchmark that
trusted them would have published a raw-route cost measured on a route that was being blocked.

**FIXED after this run — see the addendum at the end of this file.** The server cannot learn the
live session id from its own environment, so the hook now tells it.

## What this does and does not transfer to

The Finding 1 guard bug is environment-shaped, not repo-shaped: it reproduces on any repo where
the MCP server outlives the session that launched it, which is most long sessions. It has nothing
to do with size.

Finding 2's per-agent attribution is likewise repo-independent, with one stated limitation:
`byAgent` groups on `agent_type` only, and `agent_id` — though stored in `tool_call_events` — is
never read back. Two parallel instances of the *same* agent type merge into one row. Harmless for
this skill (two distinct probe types) and wrong for anything that fans out several instances of
one reviewer, which `dotnet-review` does by design.

## Addendum — Finding 1 fixed and verified, same day

`meter-tool-call` now sends `guardSessionId`: the id resolved **in the hook process's own
environment**, which is the same value the guard hooks will later look a suspension up under, so the
match holds by construction rather than by assumption. (The payload's `session_id` was already being
sent and was deliberately not reused for this — it would assume payload and environment agree.)
`ControlServer` records it via `GuardSuspension.ObserveSessionId`, and `CurrentSessionId()` prefers a
hook-reported id over this process's inherited one. Until a hook has reported one,
`SessionIdIsConfirmed` is false and `set_hook_guards` also writes the unscoped file *and says so in
its scope sentence* — a wider suspension the caller is told about beats a scoped one that silently
does nothing.

Session scoping was kept, not traded away: a subagent's hook process was confirmed by direct
observation to carry the same `CLAUDE_CODE_SESSION_ID` as the main thread, so scoping still isolates
unrelated sessions.

Verified live after an MCP restart:

| Check | Result |
|---|---|
| suspend's scope sentence | "for this Claude Code session only" — emitted only when `SessionIdIsConfirmed`, so it is itself evidence the hook → control channel → server path works |
| state file written | `guards-suspended-until.9ddc8510-…`, the live session id (was `183950ec-…`) |
| suspended: `head` on a `.cs` file | **allowed** — the exact call denied during this run |
| restored: same call | **denied**, guard message intact |

`dotnet-performance` Step 2 now runs that guarded-read check itself before launching the raw probe
and aborts if it is denied, because the two server-side instruments cannot see a hook and both
corroborated the failure. Contract bumped to `ctx-contract/3.96`; 567 tests pass, 3 new.

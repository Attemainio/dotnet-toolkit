## Where the raw route wins

- **Q1, exact-name lookup.** A `grep -rn "class Schema"` is one call against `search_index` +
  `get_symbol`. This is the row the protocol predicts should be close or a raw win, and it is — small,
  honest, and expected.
- **Q7, the "safe to delete" question, on correctness rather than cost.** This is the more important
  finding. `get_references` reports reference edges the indexer tracks; it does not — and structurally
  cannot — know that an xUnit `[Fact]` method is invoked by the test runner's reflection, because that
  invocation leaves no call-site edge in source for anything to index. The raw probe's advantage here
  wasn't broader text search — it was that reading the actual file surfaced the `[Fact]` attribute
  in the same view as the method body, prompting the domain inference. The MCP tool's answer was
  confidently stated and wrong for a real-world "can I delete this" decision. This is the honest,
  hard-to-avoid case the "where raw wins" section exists to surface: a route can be exactly right about
  what it measured (zero call-site references) and still wrong about the question actually asked.

No other row favored the raw route. Q2–Q6 and Q8 replicate the pattern the plugin's design claim
predicts: concept search beats guessing at grep patterns, one `get_symbol` call returns a full
multi-file partial type where grep needs a follow-up read per file, and `get_references` sees dispatch
edges (even though this particular Q5 didn't end up testing any) without a human eyeballing each hit
for false positives.

## What this does and does not transfer to

This is a **152-file, 246-type repo** with a largest file of 2804 lines — mid-small by industry
standards. The margins here should not be assumed to hold at very different scale:

- **On a much smaller repo** (tens of files), Q1-style exact-name lookups would dominate the question
  mix, and the raw route's per-call cheapness would likely close most of the gap — `grep` on a small
  tree is already fast and the indexer's setup cost buys less.
- **On a much larger repo**, Q4 and Q5's advantage should widen further: a partial class fragmented
  across three or more files, or a method with real interface/virtual dispatch fan-out (which this run
  did not end up testing directly, per the Q5 note above), is exactly where grep's blindness to
  semantic dispatch and multi-file declarations turns from "more calls" into "wrong or incomplete
  answer" — the same shape as Q7's divergence, but on production code instead of a test method.
- **Q7's finding is scale-independent.** `[Fact]`/reflection-based invocation is invisible to any
  static reference index regardless of repo size; a future session relying on `get_references` to
  gate a deletion should not treat a 0-reference result as sufficient for a test method, an
  attribute-driven entry point, or anything else invoked outside plain call syntax.
